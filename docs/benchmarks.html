Benchmarks

Everything here is Amber 2.4.1. Unless a section says otherwise it was measured on one laptop (Intel Core Ultra 7 255U, WSL2, one core per run) in one sitting, and every answer was checked before its time counted. 2.6 added threads inside primitives; these tables stay one core per engine, and what the threads buy is on the performance page.

Correctness gate

Every answer is an integer that fits a float64 exactly, so the summation order can't change it. Each engine's answer is compared exactly against the C reference and a wrong one prints WRONG instead of a time; each engine also checksums its own input, so a generator slip shows up as BADDATA. You can't win a cell by computing something cheaper.

The engine matrix: 24 operations, 12 engines

The widest run there is: 24 operations against every array language and columnar engine that installs on one machine (PeachQ, ngn/k, CBQN, J, NumPy, pandas, Polars, DuckDB and a hand-written C reference), all on one thread. The spec is bench/scout/SCOUT_SPEC.md, the driver bench/scout/scout.py, and this block is generated straight from its results.json, so it can't drift from the repo.

Two rows moved the wrong way

group_10k and group_100k are 16% and 28% slower than the 2.2.0 run (26.6 vs 22.5 ms, 33.3 vs 23.9 ms). Haven't pinned it down yet, so it stays up here until I do.

Where CBQN still wins, and why

BQN has no float/int split, so CBQN keeps this dataset's 0..999 “floats” as 16-bit ints and streams a quarter of the bytes on sum_f, max_f, sort_f and sort_presorted. That's its number model more than its kernels. join_inner is a real CBQN win (2.1 vs 2.9 ms).

Two rows that flatter Amber

sum_i: Amber stores these 0..999 ints in 2 bytes each, C and NumPy read real int64. Shift the same vector past 232 so Amber has to use 8 bytes too and +/ takes 3.3 ms, which is the honest 64-bit number.

sort_f: 10M “floats” with only 1000 distinct whole values is exactly what the counting sort picks up. On random float64 the same build takes ~291 ms. Prices are whole ticks, so the fast path fires on real data too, but if you're comparing sort algorithms use the second number.

Two shortcuts that were taken out
  • +/!10000000 is O(1) in Amber. arf in src/3.c folds a sum over a range into n(n-1)/2, so the old vecsum benchmark “won” by never touching the 10M elements. All data is materialised before the clock starts now.
  • A dense-key join is just an index. With right keys 0..K-1 every array language answers with one gather while DuckDB still builds a hash table. Right keys are sparse and unsorted now, so everyone does a real lookup.

Measured by someone else

Everything else on this page is Amber measuring itself against a spec in this repo. The Array Language Benchmarks Game isn't: its author picks the problems, writes the rules, runs every entry on their own machine (an i5-1135g7, 2 GB cap) and publishes the table. Amber has four entries there next to BQN, growler/k, Goal, q, Kap and C: spectralnorm and collatz in the current round, knucleotide and nbody in round 1.

The figures aren't copied here because the round is open and they move every week; read them on the game's own site, next to every entry's source. There's no restriction on algorithms, so a row compares two programs at least as much as two languages.

Against NumPy, on a real workload

One application kernel instead of a synthetic suite: a structured-payoff backtest, against a line-for-line NumPy port of the same algorithm (same tensor, same three scans, np.maximum.accumulate where Amber uses maxs). NumPy 2.5.2, both on one core, warm, best of repeated runs. It isn't flattering everywhere, which is the point.

Running a product: Amber wins once there are enough observations

Amber pays a fixed cost per operation (allocate, dispatch) that barely moves as the data inside it grows; NumPy's per-operation cost is tiny, so its time tracks the data. Time per basket:

Observations612244896120
Amber µs1,0401,1641,2301,3911,9002,388

Amber ÷ NumPy4.6×2.5×1.0×0.43×0.27×0.26×

Amber's cost goes up 2.3× while the data grows 20×; NumPy's goes up 40×. They cross at about 24 observations (it was ~43 a few releases ago). A three-year quarterly note has 12 and belongs to NumPy; a ten-year monthly one has 120, where Amber is 3.8× faster.

Read it the right way round

Both halves are the same code. Amber's cost is about how many primitives you call, not how much data each one touches. Writing fast Amber turns that into a rule you can apply.

Float scans

Up to 2.0 every float +\, *\, &\ and |\ (so sums, prds, mins, maxs on doubles) went through a generic loop that boxed an atom per element. Since 2.1 they're native. Same laptop, 2.0.1 against 2.4.1, best of 7:

Multicore: what peach buys you

A basket sweep is embarrassingly parallel. peach is a persistent thread pool now (no fork, no copying the tensor to a child), so even one basket per task pays off. 400 baskets through the payoff kernel above, best of 5:

400 baskets2 threads4 threads14 threads
serial each465 ms487 ms451 ms
peach, one basket per task391 ms314 ms215 ms
peach, 4 chunks366 ms311 ms299 ms
peach, 14 chunks378 ms324 ms232 ms

Same 400 answers in every configuration. It tops out around 2.1× on this laptop (2 performance cores, the rest efficiency cores); on heavier per-item work it scales further, e.g. {avg x?1.0} over 8 × 800k draws goes from 25.1 ms to 6.2 ms on 8 threads (4.0×).

Running them yourself

shell
./amber bench.k                        # sorted attributes vs plain find
./amber demo/hft_demo.k < /dev/null    # the HFT run (edit N at the top)
python3 bench/scout/scout.py --build    # the 24 x 12 engine matrix
python3 bench/run_comparative.py        # the ten-engine CI table
bash bench/run_suite.sh                 # vs numpy, pandas, Polars, DuckDB
./amber bench-std.k                     # moving windows, sorts

The per-engine query files are in bench/queries/, separately tuned scripts rather than one file reused, and each amber_*.k says in its header what was tried and why.
