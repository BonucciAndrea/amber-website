Benchmarks

The first section below is somebody else's measurement, on somebody else's machine. Every number after it comes out of bench/run_comparative.py, which CI re-runs on every push; the workloads, the data model and the fairness rules are specified once in bench/SPEC.md, and every engine implements that document and nothing else.

Correctness gate

Every answer in the suite is an integer that fits in float64 exactly, and every sum is over such integers, so the result is independent of summation order. SIMD pairwise, Kahan-compensated and naive left-fold summation all produce the identical bit pattern. The harness therefore compares answers exactly against the C reference and prints WRONG in place of a time for any engine that disagrees. Each engine also emits a checksum of its input data, so a divergence in the generator is caught separately (BADDATA). You cannot win a cell in this table by computing something cheaper.

Measured by someone else

Everything else on this page is Amber measuring itself against a specification written in this repository. The Array Language Benchmarks Game is not that. Jack Andrews (@effbiae) sets the problems, writes the rules, runs every entry on his own machine and publishes the table. Amber is entered there next to BQN, growler/k, Goal, q, Kap and a hand-written C program.

Amber has four entries: knucleotide and nbody from Round 1, which is closed, and spectralnorm and collatz in the current round, which is open. Each is one file in the game's own repository, sitting next to every other language's answer to the same problem.

The figures are not repeated here. The current round is open, so they move as people contribute: an entry gets rewritten, someone answers it with a better one, the board changes that week. The table, the source of every entry and the exact harness are on the game's own site, which is where they should be read from, and Round 1 is archived at r1.html.

What a placing here does and does not tell you

These are four small programs. The game puts no restriction on the algorithm, unlike the Computer Language Benchmarks Game it borrows its shape from, and every entry is written by whoever felt like contributing one. So a row compares two programs at least as much as it compares two languages, and a faster row can mean a better algorithm, a more practised author, or an engine that happens to suit that shape of work. None of it says one language is better than another, and a language with no entry in a row is absent rather than slow.

Every entry links to its own source, which is the useful part: you can read what Amber did and what BQN did and see where the difference came from. All of it runs on an i5-1135g7 under a 2 GB cap, which is not the machine anything else on this page was measured on, so these numbers do not belong in the same table as the ones below.

Amber is reported twice, on purpose

Amber is array-primitive code, the fair peer of ngn/k, CBQN, J and Uiua. Amber qSQL routes the same workloads through the select … by … from layer, the fair peer of DuckDB's SQL planner. Publishing only the faster of the two would mean picking whichever comparison flatters Amber; the gap between the rows is the query layer's overhead and it is meant to be visible.

The full engine matrix: 24 operations, 12 engines

The widest run in the project: 24 operations against every array language and columnar engine that could be installed on one machine (PeachQ (Rayforce), ngn/k, CBQN, J, NumPy, pandas, Polars, DuckDB and a hand-written C reference), specified once in bench/scout/SCOUT_SPEC.md and driven by bench/scout/scout.py. Every engine implements that document and nothing else, every engine runs one thread, and every cell is gated on a bit-exact answer against the C reference.

This run is the 2.4.0 build. Against the 2.2.0 run on the same laptop, distinct_100k got 4.6× faster, mmax_64 and sort_presorted about 2×, the moving sums and averages 1.4–1.5×, find 1.5× and sort_f 1.4×. Amber now beats CBQN on 15 of the 20 operations both implement (was 12), and is the fastest of all twelve engines on 13 of 24 (was 9).

Where CBQN still wins, and why

BQN has no user-visible float/int distinction, so CBQN stores this dataset's 0..999 “float” values as 16-bit integers and streams a quarter of the bytes on sum_f, max_f, sort_f and sort_presorted. Those cells are a property of its number model rather than of its kernels. At equal width Amber's +/ is at the memory roofline and CBQN's is a scalar loop. Everywhere else the earlier gap closed or reversed.

Two rows that flatter Amber, and why

The same disclosure the other way round. sum_i is not a pure kernel comparison: Amber narrows integer storage to the value range, so these 0..999 values occupy 2 bytes each against the genuine int64 that C, NumPy and pandas read. Amber streams a quarter of the bytes. At equal width, the same vector shifted past 232, Amber's +/ takes 4.4 ms, which is the honest number for a 64-bit reduction. The narrow storage is real and useful; it is just not what +/a measures.

sort_f is not a general sorting comparison: this dataset's 10M “floats” hold only 1000 distinct integral values, exactly the shape 2.1.0's counting sort recognises, which is why the figure moved 197 → 58 ms in that release. On random float64 the same build takes ~864 ms. Market prices are integral ticks, so the fast path fires on real data too, but a reader comparing sorting algorithms should use the second number.

Two shortcuts that were removed

Both were in the previous suite, both are documented in SPEC.md, and both are the kind of thing a benchmark table quietly relies on unless someone goes looking.

  • +/!10000000 is O(1) in Amber. src/3.c's arf constant-folds a sum over a range into the closed form n(n-1)/2. The old vecsum benchmark was exactly that expression, so Amber "won" it by never touching 10M elements while every other engine ran a real reduction. All data is now materialised before the clock starts.
  • A dense-key "join" is just an array index. With right keys 0..K-1, every array language answers the join with a single gather while DuckDB still builds a hash table. Right keys are now sparse and unsorted, forcing a genuine key lookup everywhere.

Against NumPy, on a real workload

The table above is a synthetic suite. This section is a single application benchmark, a structured-payoff backtest kernel, measured against a line-for-line NumPy port of the same algorithm. Same tensor, same three cumulative scans, np.maximum.accumulate where Amber uses maxs. It compares engines, not approaches, and it is the honest place to look because the answer is not flattering everywhere.

Intel Xeon 2.10 GHz, two cores, 8 GB. Amber built portable -O3 -flto with OpenMP; NumPy 2.4.4. Single-threaded, warm, best of repeated runs.

Where Amber wins: many observations

The two engines scale differently, and the difference is structural rather than incidental. Amber carries a high fixed cost per operation, allocating an intermediate and dispatching a kernel, but that cost barely moves when the data inside the operation grows. NumPy's per-operation overhead is tiny, so its cost tracks the data almost exactly.

Amber's cost rises 1.9× while the data grows 20×; NumPy's rises 13×. The crossover sits at roughly 43 observations. A three-year quarterly note has 12 and belongs to NumPy; a ten-year monthly has 120, where Amber is 1.8× faster.

Read this the right way round

Both halves of that table were true of the same code. The lesson is not that one engine is faster. It is that Amber's cost model is dominated by how many primitive calls you make, not how much data each one touches. Writing fast Amber is the page that turns that into a rule you can apply, and the same kernel rewritten against it beats NumPy at every size on this workload.

Native float scans

Until recently the fast scan path was gated on integer and char data only, so every float +\, *\, &\ and |\, which is to say sums, prds, mins and maxs on doubles, fell through to a generic loop that allocates an atom and goes through the generic dyadic apply once per element. It measured 57 ns per element against 0.69 ns for the identical scan on longs.

Multicore: when peach does not help

A basket sweep is embarrassingly parallel, so peach looks like free speed. On two cores it is not:

400 baskets, 2 coresWall timevs serial
serial each559 ms1.00×
peach, one basket per task772 ms0.73×
peach, 2 chunks722 ms0.77×
peach, 4 chunks746 ms0.75×

Results were byte-identical in every configuration, so this is a cost problem and not a correctness one. peach forks, and the per-task cost of handing a slice of a 17 MB tensor to a child and collecting its result exceeds what a second core buys at this granularity. Chunking reduces the task count but not the copy. For throughput, run several amberd processes and shard the work across them rather than reaching for peach.

Running them yourself

./amber bench.k                  # attribute / find speedups
./amber bench-fin.k              # the finance module
./amber bench-std.k              # moving windows, sorts
bash bench/run.sh                # cross-engine sanity + speed vs numpy / pandas / polars / duckdb
python bench/run_comparative.py  # the ten-engine CI table

The per-engine query files live in bench/queries/ and are separate, independently tuned scripts rather than the same file reused. Each amber_*.k documents in its header what optimisation was tried, what was measured, and why.
