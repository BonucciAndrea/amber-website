Benchmarks

Every number on this page comes out of bench/run_comparative.py, which CI re-runs on every push. The workloads, the data model and the fairness rules are specified once in bench/SPEC.md; every engine implements that document and nothing else.

Correctness gate

Every answer in the suite is an integer that fits in float64 exactly, and every sum is over such integers, so the result is independent of summation order — SIMD pairwise, Kahan-compensated and naive left-fold summation all produce the identical bit pattern. The harness therefore compares answers exactly against the C reference and prints WRONG in place of a time for any engine that disagrees. Each engine also emits a checksum of its input data, so a divergence in the generator is caught separately (BADDATA). You cannot win a cell in this table by computing something cheaper.

Against kdb+/q — the reference itself

kdb+/q is the system Amber's q-layer is shaped after, and the one everyone asks about. It is proprietary, so it has never been in the cross-engine CI harness below. This section is different: it is a direct, like-for-like run against a real kdb+ 4.0 on the same machine, on a q/HFT-shaped workload — a million- and ten-million-row trade table, grouped and filtered by symbol, the query an actual tick desk writes.

New in 2.0.0 — the symbol-grouping fix

Grouping a table by a symbol column used to lexically string-sort the symbols (O(n log n) with a character comparison at every step). 2.0.0 groups by the interned 4-byte id instead — equal symbols have equal ids, so the partition and the first-appearance key order are byte-for-byte identical, just found without the string sort. select … by sym went from 587 ms to 34 ms, and the whole group-by row below moved ~17×.

Method. Identical data, generated by the same closed-form formula in both engines (no RNG — 100 symbols, deterministic prices), so the inputs are bit-for-bit the same; the answers were checked equal before timing. Minimum of 5 warm reps, milliseconds, kernel time only (data generation and startup excluded). Machine: this dev box, x86-64, gcc-13 native (-march=native) build. Reading it: Amber's ngn/k core matches or beats kdb on raw array work (sort, sum) — at 10M it sorts a table in 521 ms vs kdb's 1,136 ms. The remaining distance is the group-by aggregation layer: Amber's group is still sort-based, where kdb uses an O(n) hash group. That hash-group kernel is the next optimisation on the list — see MISSING.md.

Amber is reported twice, on purpose

Amber is array-primitive code — the fair peer of ngn/k, CBQN, J and Uiua. Amber qSQL routes the same workloads through the select … by … from layer — the fair peer of DuckDB's SQL planner. Publishing only the faster of the two would mean picking whichever comparison flatters Amber; the gap between the rows is the query layer's overhead and it is meant to be visible.

The full engine matrix — 23 operations, 14 engines

The section above is a like-for-like duel with kdb+/q on the workload a tick desk actually runs. This is the widest run in the project: 23 operations against every array language and columnar engine that could be installed on one machine — kdb+/q, PeachQ (Rayforce), ngn/k, CBQN, J, NumPy, pandas, Polars, DuckDB, and a hand-written C reference — specified once in bench/scout/SCOUT_SPEC.md and driven by bench/scout/scout.py. Every engine implements that document and nothing else.

Bit-exact correctness gate

Every answer is an integer that fits in float64 exactly, so the result is independent of summation order — SIMD pairwise, Kahan-compensated and naive left-fold summation all produce the identical bit pattern. Answers are compared bit-exactly against the C reference and an engine that disagrees gets WRONG instead of a time. Each engine also checksums its input, so a divergence in the generator is caught separately. The one exception is mavg_256: a moving average divides by a growing window count, so it is genuinely order-dependent and is compared at a relative tolerance of 1e-9.

Reading these numbers honestly

CBQN's numbers are not float64 numbers. BQN has no user-visible float/int distinction: an array of 0..999 is stored as narrow integers (i8/i16) and CBQN's kernels run on that storage. On this dataset it streams roughly a quarter of the bytes the float64 engines stream, and its sort is a range-detected counting sort rather than a comparison or radix sort over 64-bit keys. That is a real and worthwhile property of the implementation, but the CBQN cells on sum_f, sum_i, max_f, sort_f, sort_presorted, distinct, member and group_10 are not like-for-like with the float64 engines.

One engine is missing. l (lv1.sh) was downloaded and checksum-verified, but the only published Linux artefact is an AVX-512 build and this CPU has none. It is a K/q-family runtime built around compressed vectors and fused execution, so it is the single most relevant engine still absent from this comparison.

Two shortcuts that were removed

Both were in the previous suite, both are documented in SPEC.md, and both are the kind of thing a benchmark table quietly relies on unless someone goes looking.

  • +/!10000000 is O(1) in Amber. src/3.c's arf constant-folds a sum over a range into the closed form n(n-1)/2. The old vecsum benchmark was exactly that expression, so Amber "won" it by never touching 10M elements while every other engine ran a real reduction. All data is now materialised before the clock starts.
  • A dense-key "join" is just an array index. With right keys 0..K-1, every array language answers the join with a single gather while DuckDB still builds a hash table. Right keys are now sparse and unsorted, forcing a genuine key lookup everywhere.

Running them yourself

./amber bench.k                  # attribute / find speedups
./amber bench-fin.k              # the finance module
./amber bench-std.k              # moving windows, sorts
bash bench/run.sh                # cross-engine sanity + speed vs numpy / pandas / polars / duckdb
python bench/run_comparative.py  # the ten-engine CI table

The per-engine query files live in bench/queries/ and are separate, independently tuned scripts — not the same file reused. Each amber_*.k documents in its header what optimisation was tried, what was measured, and why.
