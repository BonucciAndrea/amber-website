On-disk data

Amber stores a table as one file per column, in a directory, with symbol columns kept as integer indexes into a database-wide sym file. The layout is kdb+'s, deliberately: Amber reads a database q wrote, and writes one q can read. This page is the whole of it — the file format, what a read actually costs, how a write survives a crash, and what each of the four column kinds is worth.

binary format since 2.7 kdb+ compatible mmap reads crash-safe writes

Three storage shapes

Everything on disk is one of three things, and the verb you use picks which. There is no database-wide catalogue to keep in step: the directory tree is the schema.

The column file

Since 2.7 a column is a binary file: a fixed header, then the payload with no padding. `wcol writes it and `rcol reads it back (both in src/dsk.c). The header names one of four kinds, and the kind decides whether reading the column is a memory map or real work.

The attribute byte survives the round trip. A column written from a value carrying `s (sorted), `u (unique), `p (parted) or `g (grouped) comes back carrying it, so a query that could skip a scan still skips it after a reload — the point of an attribute is not having to re-derive it.

Symbols and the sym file

Symbol columns are not stored as text. Each database has one sym file holding every distinct symbol it has ever seen, and a symbol column stores a 4-byte index into it. This is kdb+'s enumeration, and it is why a sym column costs 4 bytes a row however long the names are, and why two tables in the same database can be compared and joined on symbols without any string work.

Reading: what it costs

dload gives you the whole table; dcols gives you named columns only. Because the columns are separate files, the ones you leave out cost nothing at all — not a read, not a map, and for a symbol column not the resolve either.

u:dload "db/trades"          / every column
v:dcols["db/trades";`px`sz]  / two columns; the sym column is never touched
w:dcols["db/trades";`px]     / one

Measured on a 5,000,000-row table of sym (1,000 distinct), px (float64) and sz (int64) — the best of three warm runs, in milliseconds:

operationmswhat it costs
dload — open the whole table7.9resolving 5M symbol indexes; the numeric columns are only mapped

The eager-resolve trade

Amber pays about 1.6 ms per million rows at open to turn a symbol column into symbols, and nothing afterwards: every query over that column then compares resolved symbols directly. The cost is front-loaded rather than spread across the queries. So if you open a table and run many queries over it you pay once — and if you open a table to read two numeric columns out of twenty, dcols means you do not pay it at all.

Writing atomically

A failed write must never leave half a table. splay (and set on a path ending in /) writes every column to a temporary file, syncs them, and only then renames them into place — the sym file first, so no column can reference a name that is not yet durable, and .d last, so a table is only valid once all of its columns are.

splay["db/trades";t]          / Amber's name
`:db/trades/ set t            / q's name, same thing
`:db/cfg set `a`b!1 2         / no trailing slash: one file, any value
Symbols are enumerated for you

Amber's set and splay enumerate symbol columns against db/sym themselves. In kdb+ you must remember .Q.en first, and set on a table with un-enumerated symbols is a 'type.

Appending, and the journal

upsert on a path adds rows to the end of the existing column files rather than rewriting the table, so appending costs the new rows and not the history. Because that is an in-place mutation of several files, it is journalled.

`:db/trades/ upsert newrows    / rows onto the end of each column file

Partitioned databases

A partitioned database is a directory of date (or int) directories, each holding splayed tables, all sharing the one sym file at the root. loaddb maps the whole thing; a query over a date range only ever touches the partitions in that range.

Q.dpft[`:db;2026.01.03;`sym;`trades]   / save one partition, parted on sym
loaddb "db"                             / map the database: every table, every partition
t:ptab`trades                           / all partitions of one table, as a single table

Locking

Everything that adds symbols or rewrites a table takes the database's lock first, so two processes writing into one database cannot lose each other's symbols or interleave a rename with a read. The lock is held for exactly the span that needs it — from reading the sym file to writing it back — and an error inside that span releases it on the way out rather than leaving the database wedged.

What the lock does not cover

Readers are not blocked, and do not need to be: a reader only ever sees a fully renamed file. The lock serialises writers against each other. A reader that mapped a column before it was replaced keeps reading the bytes it mapped, which is the usual mmap-plus-rename behaviour and not a torn read.

Querying on disk

A mapped table is an ordinary table — qSQL does not know or care that its columns came from files, and the pages fault in as the query reads them. So the on-disk and in-memory stories are the same one:

u:dload "db/trades"
sel"select sum px by sym from u"
sel"select from u where sym=`msft, px>100"

Two things are worth knowing for query speed. A column carrying `s or `p keeps that attribute through the round trip, so a range constraint on a sorted column stays a binary search after a reload. And select with a by reaches Amber's fused group-aggregate, which hashes the key once and makes one pass per aggregate — which is why the group-and-sum row in the table above is 4 ms rather than the 40 ms a hand-written group-then-sum idiom costs.

Reading a kdb+ database

Amber reads q's files directly — \l db on a database kdb+ wrote works, with no conversion step. Three on-disk layouts are recognised by their leading bytes: q's flat vector, q's enumerated column, and q's serialised-value form used for the sym file and .d. q's types map onto Amber's, and the temporals keep the same numbers.

It also writes back in kind: if a database's sym file is one q wrote, Amber writes q-format column files into it, so a database can be shared by both engines rather than forked. Talking to q covers the rest of the interop — IPC, log replay, and loading a database q wrote. Files Amber wrote before 2.7, when the format was text, still read through dget and dload; get reads only the binary format and never evaluates a file, as q's get does not.

Worked example

A tick database from nothing: write two days, append to one, then query across both.

Load order

hdb.k builds on the base library, so load amber.k and sys.k first, and qsql.k too if you want sel. A bare \l hdb.k is resolved against $AMBER_HOME, or the directory holding the amber binary, so it works from any working directory once AMBER_HOME is set. splay creates the directories it needs — you do not have to mkdir a partition first.

tick.k
\l amber.k
\l sys.k
\l hdb.k
\l qsql.k

/ a day of trades
mk:{[n]+`sym`px`sz!(`msft`aapl`goog@3!!n;100+0.01*!n;100*1+10!!n)}

/ two partitions, written atomically, symbols enumerated for us
splay["db/2026.01.03/trades";mk 1000000]
splay["db/2026.01.04/trades";mk 1000000]

/ a late batch onto the second day: costs the new rows, not the day
`:db/2026.01.04/trades/ upsert mk 50000

/ read one day, two columns -- the sym column is never resolved
v:dcols["db/2026.01.04/trades";`px`sz]
+/v`px

/ read it whole and group by symbol
u:dload "db/2026.01.04/trades"
sel"select vwap:(+/px*sz)%+/sz by sym from u"

The two splay calls leave nothing behind if the process dies mid-write; the upsert either adds all 50,000 rows or none; and the dcols read touches two files and ignores the third.
