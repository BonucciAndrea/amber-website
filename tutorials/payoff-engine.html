A structured-payoff engine on Amber

A worst-of autocallable is a product whose entire lifecycle — did it redeem early, how many coupons did it bank, what did it pay — is three cumulative scans over a matrix. This is what that looks like when nothing loops, and what the engine did with it.

The shape of the problem

An autocallable on a basket of shares observes the basket on a schedule. At each observation, if the worst performer is above the autocall level, the note redeems and pays accrued coupons. If it survives to maturity, a barrier decides whether the investor gets capital back or the basket's performance.

Backtesting it means asking the same question from every possible start date. With 1,800 start dates and twelve quarterly observations, that is a 1,800 × 12 grid of "how had the basket performed by this observation" — and every product feature is a scan across the second axis.

Product featureArray operation
Did it autocall, and when?running any of (performance > level), then count
Memory couponsrunning max of (hit × observation index)
Plain couponscumulative sum of hits
Barrier at maturityfinal column compared to the barrier level
Worst-of basketmin-reduce across the basket's members

Compute the tensor once

The expensive object is the performance tensor: for every name in the universe, every start date and every observation, the ratio of the price then to the price at inception. Build it once for the whole universe and every basket afterwards is a min-reduce over three slices of it.

demo/btc.k
/ tensor: U x n x S.  Each column is one whole-vector divide.
cTensor:{[px;S;off]
  {[p;S;off] d:p@S; {[p;S;d;o] (p@S+o)%d}[p;S;d;]'off }[;S;off]'px}

/ worst-of basket: min-reduce across the chosen names
cWorst:{[PC;b] (&/) PC b}
Note the storage order

That tensor is column-major — n columns of S values, not S rows of n. The first version of this engine was the other way round and ran ten times slower for exactly that reason. Writing fast Amber is the general form of the lesson; this page is where it was learned.

The lifecycle, in three scans

Redemption timing is a running any across observations, which is a running max on booleans, which as columns is n−1 whole-vector maxes. Counting how many observations stayed live is a sum across the same columns.

demo/btc.k
cStop:{[lvl;pc]
  hit: pc >' lvl;              / n whole-column compares
  rdm: (|\)hit;                / n-1 whole-column maxes
  nrd: (+/)rdm;                / n-1 whole-column adds
  ((#lvl) - nrd; 0 < nrd) }

Coupons differ only in which scan they use — memory coupons remember the highest observation index that ever hit, plain coupons count hits — so the product feature is a branch selecting a scan, not a different code path:

demo/btc.k
cCpn:{[lvl;mem;pc;sp]
  hit: pc >' lvl;
  cm:  $[mem; (|\)(hit *' 1 + !#lvl); (+\)hit];
  cPick[cm;sp] }

And redemption value needs the final fixing, which in column-major storage is simply the last column — an index, not a computation:

demo/btc.k
cVal:{[Q;pc;cp;cl]
  fp: *|pc;
  pr: cl | fp > Q`barLvl;
  (cp * Q`cpnAmt) + pr + (1 - pr) * fp }

The whole kernel is about sixty lines. There is no loop over start dates, no loop over observations and no loop over rows — the only iteration in the system is over baskets.

Against a faithful NumPy port of the same algorithm at 626 µs per basket, this is 2.1× faster. The benchmarks page has the full comparison including the sizes where NumPy wins.

Those numbers matter mostly because of what they make interactive. Re-running a product after an edit takes about 1.4 ms. Sweeping every single-name substitution across a hundred-name candidate pool — 291 baskets, which is the question a distributor actually asks — lands in under half a second. That is the difference between a tool someone explores with and a job someone submits.

What the sweep changed about the product

Worth recording, because it was not the expected result. The obvious way to rank alternative baskets is by median IRR. Running the sweep proves that is close to useless: an autocallable's upside is capped at the coupon, so 99% of 4,000 sampled baskets land within one percentage point of each other on median return.

The measure that discriminates is the probability of capital loss, which ranged from 0% to 69.4% across the same baskets. The tail is where the difference lives, and the fast sweep is what made it visible.

Source

The kernel is demo/btc.k in the Amber repository, with demo/bt.k kept alongside it as the row-major original — the two are differentially tested against each other, and the pair is the clearest illustration of the cost model on this site.
