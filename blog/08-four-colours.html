On array languages

Checking the four colour theorem with arrays

A proof of the four colour theorem ends in a program that checks 2822 small graphs. Here is that program, moved from Python loops to Amber columns: over 100 times faster on every ring size both versions finished, and small enough to run on this page.

algorithms 2026-09-21·16 min read ·Andrea Bonucci

The four colour theorem says that any map drawn on a plane can be coloured with four colours so that no two countries sharing a border get the same colour. It was the first major theorem proved with a computer, and every proof since has kept a large mechanical core: a list of small graphs, each of which has to be checked, one by one, by a program.

In 2023, for a bachelor project in computer-assisted proofs, four classmates (Abel, Tomas, Lex and Jordy) and I wrote one of those programs in Python: github.com/BonucciAndrea/DurreHeesch, with the mathematics written up in our report (PDF). It runs the Dürre–Heesch reducibility check on Steinberger's 2822 configurations, and it did the job: every one of them checked out as D-reducible, after a twelve-hour run on a high-end PC. One configuration at a time it is not fast, though: about three minutes for a 13-vertex ring on today's machine, and hours once the rings reach 15 or 16. This post rewrites it in Amber. It is not a line-by-line translation. Every step of the algorithm becomes an operation on whole columns: all ring colourings at once, every Kempe interchange at once. On the configurations both versions have finished, the Amber one is over 100 times faster at every ring size. At the bottom of the page is the checker itself, running in your browser.

The proof in one paragraph

Suppose some map needs five colours, and take the smallest one. Two facts about it give a contradiction. First, unavoidability: any such map must contain at least one graph from a fixed list. Steinberger found a list of 2822. Second, reducibility: a smallest counterexample cannot contain any graph from the list, because if it did you could shrink the map, colour the smaller one with four colours, and extend that colouring back. Every configuration on the list must therefore pass a reducibility test. This post is about the test Steinberger's list was built for, called D-reducibility. The other half, unavoidability, is a separate discharging argument, and it is not what this code checks.

A configuration is a small planar graph: a ring of 6 to 16 vertices around some interior vertices. The question is about the ring. Take every way to colour the ring with four colours. Some of those colourings extend straight into the interior. The rest have to be rescued: swap colours along Kempe chains until the ring colouring turns into one that is already known to be good. If every ring colouring is eventually good, the configuration is D-reducible.

What a configuration looks like

U_2822.conf lists each configuration as a header followed by one line per vertex. The first is Birkhoff's diamond, 10 vertices with a 6-ring:

In Amber a configuration is one list, (V;R;E;adj), with 0-based neighbour lists. The browser version at the bottom of this page carries five of them. The native script reads all 2822.

Step 1: every colouring of the ring, at once

Renaming the colours doesn't change anything, so only essential colourings are counted: colour 0 comes first, and each new colour is the next unused one. For a ring of n there are (3n−1+5)/8 of them when n is even and (3n−1−1)/8 when it is odd. That is 1,793,614 for n = 16.

The Python builds them recursively, one list at a time. Amber grows all of them together: each step triples the column (every colouring gets each of the three colours that differ from its last one), then keeps the rows that respect the first-use order. The state is three vectors, a base-4 code, the last colour and the highest colour so far:

dh.k
step:{c:x 0;l:x 1;m:x 2;nl:(4!l+1),(4!l+2),(4!l+3);m3:m,m,m;k:&~nl>m3+1;(((4*c,c,c)+nl)@k;nl@k;(m3|nl)@k)}
ess:{[n]s:(n-2) step/(,1;,1;,1);c:s[0]@&~0=s 1;{4!_x%y}[c]'|*\1,(n-1)#4}

That builds all 1.79 million ring-16 colourings in 0.12 s. The Python's setup, which builds these colourings and their block tables, takes 53 s.

The other half of the trick is how a colouring is found later. Python stores the good colourings in a tree and walks it, one colour at a time. Amber gives each colouring a number: the steps between neighbouring colours are each 1, 2 or 3, so the colouring reads as a base-3 number. "Is this colouring good?" becomes one array lookup, G@P@rank, which is also one lookup for a million colourings at once.

Step 2: which colourings extend inward

Python's ExtendCheck takes one ring colouring and backtracks through the interior. Amber runs a join instead. It starts with one row per ring colouring. Adding an interior vertex multiplies each row by the colours that vertex can still take: the ones not used by its ring neighbours or by interior neighbours already placed. A vertex whose neighbours are all placed can no longer constrain anything, so its column is dropped and duplicate rows are merged. When the last interior vertex is in, the ring colourings that still have a row are the ones that extend.

Every step is a filter, a gather or a distinct over a column. For a ring-12 configuration the whole step takes 15 ms. On every configuration checked, the number it finds matches the count stored in U_2822.conf exactly, and the test suite checks it against a plain JavaScript backtracking search as well.

Step 3: the Kempe chain game

Pick one of the three ways to split the four colours into two pairs, say {0,1} and {2,3}. Around the ring, consecutive vertices whose colours lie in the same pair form a Kempe sector. Inside the configuration, sectors of the same kind may be joined by Kempe chains; the sectors joined together form a block. Which groupings are possible is a theorem (6.6.4 in Fritsch & Fritsch, The Four-Color Theorem): a grouping of the sectors is a block decomposition exactly when every block holds sectors of one type, no two blocks interleave around the ring, and two blocks that touch at one point touch at exactly one more. Our report (§2.2) turns each decomposition into a sequence of up and down arrows, one per sector, with as many ups as downs and never more downs than ups in any prefix. Those are Dyck words, so a ring with m sectors has Catalan(m/2) decompositions: 1, 2, 5, 14, 42, 132 for 2 to 12 sectors. The code generates them from the arrows, and the test suite checks the result against the theorem directly.

Swapping the two colours of each pair throughout a block gives another proper colouring. A ring colouring becomes good if there is some partition such that, whatever the true block decomposition is, some combination of block swaps turns it into a colouring that is already good. Repeat until nothing changes. The report calls the sets this builds Φ0 ⊂ Φ1 ⊂ …; if the last one holds every ring colouring, the configuration is D-reducible. Birkhoff's diamond gets there in five rounds, 16 → 21 → 23 → 27 → 30 → 31 good colourings, which is the report's Φ = Φ5.

One shortcut is safe and saves half the work. Swapping inside every block of one type just renames two colours everywhere, which gives an equivalent colouring. So one block of each type can always be left alone; the code never swaps the first two blocks.

The swap has a neat form. Colours are 0–3, and the partition that pairs 0 with q+1 swaps exactly the colours that differ by XOR q+1. A Kempe interchange is an XOR on a subset of the ring:

amber>
X:0 1 2 3 1 0 3 2 2 3 0 1 3 2 1 0          / XOR table, X@(4*a)+b
c:0 1 2 0 1 3                               / a ring colouring
chain:0 0 1 0 0 1                           / vertices 2 and 5: two {2,3} sectors
c+chain*(X@(4*c)+1)-c                       / swap them under q = 0
0 1 3 0 1 2

That is what makes the game vectorisable. The colourings are grouped by partition and by number of sectors. For each group, every allowed interchange of every block decomposition is laid out as one flat column of (interchange, colouring) cells. Each cell is XORed and relabelled, and its rank is looked up in the good-set. A block decomposition passes if any of its interchanges lands on a good colouring. The colouring passes if all of its decompositions pass. So the whole check is a gather, an any-reduce and an all-reduce.

There is a negative control. A single vertex of degree 6 inside a 6-ring is not D-reducible, and both versions say so: 11 of its 31 ring colourings extend directly, and the Kempe game can't rescue a single one of the other 20.

Making it fast

The first working version was only 10–25 times faster than Python. Four changes took it to 100×:

  • A lookup, not a tree. The base-3 rank turns every good-set test into one gather.
  • Relabelling as a state machine. After a swap, the colours must be renamed back into first-use order before the lookup. A 2,500-state table does the renaming and the rank in one pass, at two lookups per vertex.
  • Cache the interchanges. The interchanges a colouring can reach don't depend on which colourings are good. After the first round their ranks are kept, and later rounds are a single gather against the updated good-set.
  • Chunks that fit in cache. The flat columns were first built 4 million cells at a time. Cutting that to 125,000 made the whole program twice as fast. Nothing else changed; the working set simply stopped spilling out of the CPU cache.

Two caveats. First, this compares an array language with plain Python lists, not with NumPy; a careful NumPy port would close part of the gap. Second, the two programs don't do the same amount of work. Python's tree search prunes: it abandons an interchange as soon as the colours read so far leave the tree. Amber builds every allowed interchange in full and throws most of them away. At small rings that costs nothing; at rings 15 and 16 there are many more interchanges, and Amber's time grows about 10× per ring size where Python's grows about 6×. The vectorised version wins by doing more work, much faster.

For scale, the report's own timing table has configuration 27 at 2 min 7 s on a home computer, and checking all 2822 configurations took twelve hours on a high-end PC running several at once. The same configuration takes Amber 0.29 s on one core.

What parallelism adds

The configurations are independent, so the obvious move is to run several at once. With separate Amber processes, configurations 1–200 drop from 128 s to 57 s on four processes. Beyond four it stops helping, for two reasons. The slowest single configuration sets a floor. And the kernel is memory-bound: it streams large integer columns, so extra cores wait on the same memory bus.

Parallelising inside one configuration, with interchange chunks on peach, gave 2.35× on a ring-14 configuration with four threads, and more threads didn't help, for the same memory reason. That result needed one change to the engine. peach hands out work in 1024-item batches, so a job of a few dozen heavy tasks all lands on one thread. The measurement above used a build where the batch size shrinks for small jobs.

The whole program

Everything above is one file of 87 lines, with no dependencies beyond the Amber interpreter. It reads U_2822.conf, builds the colourings and block tables, and defines run1 i, which checks configuration i (0-based) and returns its number, ring size, directly extendable count, the count the file expects, the verdict and the time in ms.

Put U_2822.conf from the Python repository in the same folder as dh.k, start Amber in that folder (or point DIR on line 11 at it), load the file with \l dh.k, and run, for example, {run1 x}'!30 to check the first thirty configurations. Download the file as dh.k; the version the playground below loads is assets/dh/dh.k, the same code with five configurations written inline instead of read from disk.

Try it

This is the real checker: the Amber interpreter compiled to WebAssembly, running in your browser with the file above loaded. Pick a preset, press Run (or Ctrl+Enter), and edit anything you like. Each line is one statement; lines starting with / are comments.

  • Ring colourings builds every essential colouring of an 8-ring (274 of them) and prints the first five, one per row.
  • Check a configuration runs the whole algorithm on configuration 27, a 12-ring around 8 interior vertices. It takes a couple of seconds in the browser.
  • A graph that fails checks the degree-6 wheel. Its neighbour lists are written out so you can change them and check your own graph.
  • Kempe swap = XOR is the swap from the section above.
  • Block decompositions counts the block decompositions for 2 to 12 sectors.

check prints one line per field:

fieldmeaning
ringthe ring size R: how many outer vertices there are
extendablehow many essential ring colourings extend straight into the interior (the report's Φ0), found by the vectorised join
expectedthe same count as stored in U_2822.conf, to compare against; 0N (null) for a graph you made up
goodhow many ring colourings are good once the Kempe game stops. For D-reducibility this has to be all of them: 31 for a 6-ring, 22,144 for a 12-ring
reducible1 if every ring colouring ended up good (the configuration is D-reducible), 0 if the game got stuck
mshow long the check took in your browser, in milliseconds

A configuration is written (V;R;E;neighbours): V vertices numbered from 0, the first R of them forming the ring in order, E the expected extendable count (or 0N), and then one neighbour list per vertex. The wheel is (7;6;0N;(1 5 6;2 0 6;…;0 1 2 3 4 5)): ring vertex 0 touches its ring neighbours 1 and 5 and the centre 6, and the centre touches every ring vertex. If you edit it, keep the graph a plausible configuration: list every edge from both ends, keep the ring a cycle of at least 6 vertices, and keep every inner face a triangle. The checker will run on anything, but its verdict only means D-reducibility for a real configuration.
